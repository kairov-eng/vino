# Техническое задание: «Сканер вина» для платформы «Своё Вино»

Версия 1.0 · 15.09.2026 · Статус: согласование

Исходная постановка: конкурсное задание РСХБ.Цифра «Сканер российских вин с описанием на платформе „Своё вино“» (`10. РСХБ.Цифра.pdf`). Настоящий документ конкретизирует постановку с учётом фактически переданных данных (см. `DATA.md`) и фиксирует рамки реализации в три этапа (см. `ROADMAP.md`).

---

## 1. Цель

Построить веб-сервис, который по одной фотографии этикетки/бутылки, снятой телефоном в реальных условиях (полка магазина, наклон, блики, соседние бутылки, слабый свет), находит **ровно одну** карточку вина в каталоге «Своё Вино» и показывает её в mobile-first интерфейсе в стилистике портала. При отсутствии вина в каталоге сервис честно сообщает об этом и предлагает ближайшие аналоги.

## 2. Критерии успеха (из постановки, зафиксированы как приёмочные)

| № | Критерий | Целевое значение | Вес в оценке |
|---|----------|------------------|--------------|
| 1 | Доля точных совпадений top-1 на контрольной (приватной) выборке | 90–100 % | 50/100 |
| 2 | Стабильный отрыв score top-1 от top-2 (позволяет убрать экран выбора) | margin ощутим, метрика стабильна | входит в 1 |
| 3 | Функция после поиска (retention) | рабочая, полезная | 20/100 |
| 4 | Архитектура: разделение слоёв, воспроизводимость (Docker, README, ARCHITECTURE) | — | 15/100 |
| 5 | Дизайн: соответствие стилистике «Своё Вино», mobile-first | — | 10/100 |
| 6 | Время ответа на оборудовании команды | ≤ 3 с (цель ≤ 1,5 с на CPU, ≤ 0,7 с на GPU) | 5/100 |

## 3. Границы решения

### 3.1 В объёме

- Загрузка и индексация каталога (CSV-экспорт Strapi + медиа-файлы `uploads/` + sitemap).
- Пайплайн распознавания: нормализация фото → извлечение признаков (CV, опционально OCR) → поиск кандидатов → переранжирование → решение с оценкой уверенности.
- REST API: точка для скрипта организатора (`POST /v1/eval/predict`), расширенная точка для UI (`POST /v1/scan`), карточка (`GET /v1/wines/{slug}`), аналоги, «цифровой сомелье».
- Мобильный веб-интерфейс: экран сканирования, экран карточки, экран «не найдено / похожие», экран дополнительной функции.
- Диагностическая страница для разработчика (этап 2): показ кандидатов, метрик, промежуточных изображений.
- Оценочный контур: прогон публичного датасета, отчёт F1@1 / F1@5 / accuracy / latency.
- Документация: `README.md`, `ARCHITECTURE.md`, воспроизводимый запуск через Docker Compose.

### 3.2 Вне объёма

- Нативные мобильные приложения.
- Онлайн-переиндексация в реальном времени (достаточно CLI-команды/крона; ~50 новых позиций в день).
- Внешний деплой; демонстрация локальная.
- Полноценная интеграция в продовый Strapi портала (делаем адаптер импорта из его экспорта; структура данных совместима с сущностью `wine`).

## 4. Пользователи и сценарии

**П1 — Покупатель у полки (основной).** Открывает модуль в мобильном браузере → «Сфотографировать» → 1–3 с → карточка вина: название, винодельня, регион, сорт, цвет, категория, описание, рейтинг (если есть), подсказка «к чему подать» → дополнительная функция.

**П2 — Вина нет в каталоге.** После сканирования: «Похоже, этого вина пока нет в каталоге. Возможно, вам подойдут…» + 3–5 аналогов (та же винодельня / сорт / регион / стиль) с пояснением, почему предложены.

**П3 — Скрипт организатора.** Bash-скрипт последовательно шлёт `multipart/form-data` с полем `image`, ждёт полного ответа, принимает `{"slug":"..."}` или `[{"slug":"..."}]`, таймаут curl 10 с. Повторов нет. Сервис **всегда** возвращает лучший slug (пустой ответ — гарантированная ошибка).

**П4 — Разработчик / эксперт на демо.** Диагностическая страница: загрузка фото, top-k кандидатов с картинками, вклад каждого сигнала в итоговый score, margin, время по этапам пайплайна.

**П5 — Контент-менеджер.** Пополнение каталога: положить новый CSV/медиа → команда `ingest` → `index`; новые позиции появляются в поиске.

## 5. Функциональные требования

### 5.1 Индексация (этап 1)

- ФТ-1.1 Импорт CSV `strapi_output0709.csv` (UTF-8 с BOM, колонки: Название вина, Категория, Цвет, Регион, Сорт винограда, Описание, Винодельня, Slug, Название фото). Дедупликация по `slug` (4147 строк → 2103 вин).
- ФТ-1.2 Сопоставление slug → файл эталонного фото по приоритету: (а) `wines_sitemap_*.xml` (`<loc>/wines/{slug}` → `<image:loc>…/uploads/{file}`); (б) транслитерация «Название фото» по правилам Strapi (`nameToSlug`, разделитель `_`) и поиск `{name}_{hash10}.{ext}` среди оригиналов (без префиксов `thumbnail_/small_/medium_/large_`); (в) ручной файл соответствий `data/manual_image_map.csv`. Позиции без фото индексируются только по тексту и помечаются `has_image=false`.
- ФТ-1.3 Разбор slug на структурированные атрибуты: винодельня-префикс, сорт, цвет, сладость (`suhoe|polusuhoe|polusladkoe|sladkoe|bryut|ekstra-bryut`), крепость (`135` → 13,5 %), объём (`07`), год.
- ФТ-1.4 Загрузка вспомогательных данных: `wineries_sitemap` (slug и обложка винодельни), `*.geojson` (полигоны регионов) — для карточки и функции «регион на карте».
- ФТ-1.5 Нормализация эталона: обрезка по альфа-каналу, выделение области этикетки, генерация набора видов (полная бутылка, этикетка, аугментированные «полевые» имитации), OCR эталона, расчёт векторов всех выбранных моделей, извлечение локальных признаков этикетки.
- ФТ-1.6 Хранение в PostgreSQL + pgvector; идемпотентный повторный запуск (upsert по slug + хэш файла).
- ФТ-1.7 Отчёт индексации: сколько вин, сколько с фото, сколько неразрешённых, группы вин с одинаковым фото (14 групп), топ дублей по имени.

### 5.2 Распознавание (этапы 2–3)

- ФТ-2.1 Приём изображения JPEG/PNG/WEBP/HEIC до 20 МБ; EXIF-ориентация; ресайз до рабочего размера.
- ФТ-2.2 Нормализация запроса: детекция бутылки/этикетки, выбор главного объекта (центральный, крупнейший), кроп с полями, коррекция экспозиции/бликов, опционально выравнивание перспективы.
- ФТ-2.3 Извлечение признаков: глобальный визуальный эмбеддинг (SigLIP 2), дополнительный эмбеддинг для instance-matching (DINOv2/v3), локальные ключевые точки этикетки, OCR-текст (если включён).
- ФТ-2.4 Генерация кандидатов: объединение top-K по каждому визуальному индексу и top-K по тексту (OCR → нечёткий поиск по названию/винодельне/сорту/году).
- ФТ-2.5 Переранжирование: геометрическая верификация этикетки (инлайеры гомографии), совпадение структурированных атрибутов (год, сладость, сорт, объём, винодельня), обученная/настроенная функция объединения сигналов.
- ФТ-2.6 Решение: `decision ∈ {match, low_confidence, not_found}` по калиброванному `confidence` и `margin`. Для `/v1/eval/predict` всегда возвращается top-1 slug.
- ФТ-2.7 Группы одинаковых фото (несколько slug на одно изображение): разрешение только по OCR/атрибутам; при невозможности — канонический slug группы (первый по алфавиту, конфигурируемо).
- ФТ-2.8 Ответ содержит: карточку, `top5` с score, `confidence.top1`, `confidence.top5`, `margin`, `timings` по этапам, `debug` (по флагу).

### 5.3 Карточка и дополнительная функция (этап 3)

- ФТ-3.1 Карточка вина: фото, название, винодельня (ссылка), регион (+ мини-карта из geojson), категория/цвет, сорта, описание, крепость/объём из slug, ссылка на портал `https://vino-svoe.ru/wines/{slug}`.
- ФТ-3.2 «Похожие/аналоги»: 3–5 вин по комбинации текстового эмбеддинга описания + фильтров (цвет, сладость, сорт, регион), с объяснением («тот же сорт и регион, другая винодельня»).
- ФТ-3.3 «Цифровой сомелье»: 2–3 наводящих вопроса (повод, блюдо, предпочтения) → рекомендация из найденного вина и аналогов, объяснение подачи. LLM через провайдер-абстракцию (OpenAI/Gemini/YandexGPT/локальная модель), строго grounded на данных каталога; при недоступности LLM — детерминированный fallback по правилам.
- ФТ-3.4 Обратная связь: «Это то вино?» Да/Нет (+ выбор правильного из top-5) → лог для дообучения и калибровки.

### 5.4 Диагностическая страница (этап 2)

- ФТ-4.1 Загрузка фото, отображение: исходник → нормализованный кроп → детекции; top-10 кандидатов с эталонными фото и разложением score; OCR-текст; тайминги; итоговое решение.
- ФТ-4.2 Пакетный режим: прогон папки с манифестом `queries.tsv` и (опционально) файлом ответов → таблица accuracy/F1@1/F1@5/latency, confusion-пары.

## 6. Нефункциональные требования

| Категория | Требование |
|-----------|------------|
| Производительность | p50 ≤ 1,5 с и p95 ≤ 3 с на CPU (8 потоков, без GPU) для фото 12 Мп; на GPU p95 ≤ 1 с. Индексация 2 100 вин ≤ 30 мин на CPU. |
| Надёжность | `/v1/eval/predict` не возвращает ошибок 5xx на валидных изображениях; при сбое любого необязательного модуля (OCR, реранкер) пайплайн деградирует до визуального поиска и всё равно отдаёт slug. |
| Воспроизводимость | `docker compose up` поднимает БД, ML-сервис, веб; одна команда `make index` собирает индекс; версии моделей и весов зафиксированы в конфиге; сиды фиксированы. |
| Совместимость | Скрипт `participant_test.sh` проходит без модификаций против `http://127.0.0.1:8080/v1/eval/predict`. |
| Переносимость | CPU-only режим обязателен (машина команды без NVIDIA GPU); GPU — опциональное ускорение через тот же код (`DEVICE=cuda`). |
| Наблюдаемость | Структурированные логи по запросу: id, тайминги этапов, top-5, decision; метрики Prometheus-формата (опционально). |
| Безопасность | Файлы не сохраняются дольше сессии без согласия (флаг для сбора датасета); лимиты размера; без внешних вызовов на горячем пути поиска (LLM — только в функции после поиска). |
| Данные | Персональных данных нет. Медиа каталога хранятся локально, в git не попадают. |

## 7. Метрики и протокол оценки

- **accuracy@1** — доля запросов, где top-1 slug верный (главный критерий организатора).
- **F1@1, F1@5** — macro-усреднённые по запросам precision/recall в top-k при единственном верном ответе (для k=1 F1@1 = accuracy@1; для k=5 отчитываем recall@5 и F1@5 = 2·P·R/(P+R), P = 1/5 при попадании).
- **margin** = score(top-1) − score(top-2); отчитываем распределение отдельно для верных и неверных top-1 (цель: разделимость → пороги).
- **Калиброванный confidence** — вероятность правильности top-1 (Platt/isotonic на валидации); ECE как контроль.
- **latency** — p50/p95 по этапам (`normalize`, `embed`, `ocr`, `search`, `rerank`, `total`).
- Валидационный набор формируется командой: 3 публичных запроса + собственная съёмка ≥ 150 фото (≥ 50 разных вин, включая near-duplicate серии: Массандра, Фанагория «100 оттенков», Родное Гнездо «4 elements», Абрау-Дюрсо) + синтетические «полевые» имитации из эталонов. Разметка — `slug`.

## 8. Ограничения и риски

| Риск | Влияние | Митигирование |
|------|---------|---------------|
| Доменный разрыв: эталон — студийная бутылка на прозрачном фоне, запрос — полка с бликами | Низкий recall без нормализации | Кроп этикетки с обеих сторон, аугментации эталона, мультивид на вино, геометрическая верификация |
| Near-duplicates (одна этикетка, разный год/сладость/объём) | Ошибки top-1 | OCR-атрибуты (год, «полусухое», объём) как жёсткие/мягкие фичи реранкера; группы одинаковых фото |
| Некачественные эталоны (42 «Screenshot_N», 5 без фото) | Часть вин не находится | Текстовый канал, флаг качества, ручная замена фото при наличии |
| Отсутствие GPU | Не укладываемся в SLA | Лёгкие модели (SigLIP 2 base/16-384, DINOv2-B, PP-OCRv5 mobile ONNX), кэш признаков эталонов, ограничение размера входа, параллелизм этапов |
| OCR медленный/шумный на декоративных шрифтах | Ухудшение времени | OCR только на кропе этикетки, ограничение по времени, асинхронно к эмбеддингу; OCR как усилитель, не как основа |
| Мало «полевых» фото для обучения | Нельзя обучить реранкер | Ручная настройка весов + синтетика; сбор фото командой; дообучение — опционально этап 3 |

## 9. Приёмка по этапам (кратко; детально в `ROADMAP.md`)

- **Этап 1.** `make ingest index` без ошибок; отчёт: 2103 вина, ≥ 2094 с фото; в БД векторы для всех моделей; юнит-тесты маппинга.
- **Этап 2.** Диагностическая страница работает; `/v1/eval/predict` совместим со скриптом; на валидационном наборе accuracy@1 ≥ 80 %, p95 ≤ 3 с на CPU; отчёт метрик в `reports/`.
- **Этап 3.** Полный сценарий П1–П3; accuracy@1 ≥ 90 % на валидации; мобильный UI в стилистике портала; функция после поиска; README/ARCHITECTURE; Docker Compose; видео-демо.
