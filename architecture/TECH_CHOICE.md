# Выбор технологий для построения векторов по фото

Цель раздела — зафиксировать, чем именно превращаем фото в признаки, почему, и как проверим выбор. Ограничение: рабочая машина команды **без GPU** (CPU-only обязателен), GPU — опциональное ускорение.

## 1. Постановка с точки зрения CV

Это **instance-level retrieval** (поиск конкретного объекта, а не класса) с сильным доменным разрывом: эталон — студийная бутылка на прозрачном фоне, запрос — полка. Каталог маленький (2–5 тыс.), поэтому стоимость поиска в векторной БД пренебрежима; вся сложность — в качестве признаков и в различении near-duplicates, где различия — 1–2 слова текста на этикетке.

Вывод: одна глобальная модель эмбеддингов не решит задачу на 90 %+. Нужен каскад: **глобальный эмбеддинг для recall → локальные признаки и текст для precision.**

## 2. Кандидаты и сравнение

Данные из открытых бенчмарков visual product search (nyris VPS Benchmark, arXiv 2603.17186, 2026) и опыта instance-retrieval:

| Модель | Тип | Размерность | Вход | R@1 SOP (product, zero-shot) | CPU-время на 1 фото* | Роль у нас |
|--------|-----|-------------|------|------------------------------|----------------------|------------|
| **SigLIP 2 SO400M/16-384 (naflex)** | vision-language | 1152 | 384 | 80,3 % | 1,5–3 с | точность при наличии GPU |
| **SigLIP 2 Base/16-384** | vision-language | 768 | 384 | ≈ 74–77 % (оценочно) | 0,3–0,6 с | **основной глобальный эмбеддинг (CPU)** |
| DINOv3 ViT-L/16 | self-supervised | 1024 | 224 | 66,6 % (но лидер на «жёстких» индустриальных наборах) | 0,8–1,2 с | — |
| **DINOv2/v3 ViT-B/14(16)** | self-supervised | 768 | 224 | ≈ 60–65 % zero-shot, 83 % после fine-tune | 0,15–0,3 с | **второй эмбеддинг: устойчив к фону/ракурсу, дополняет SigLIP** |
| CLIP ViT-L/14 | vision-language | 768 | 224/336 | ниже SigLIP 2 | 0,6–1 с | — (уступает SigLIP 2) |
| Gemini/Vertex/Cohere embeddings | API | — | — | 68–77 % | сеть 0,5–1,5 с | — (внешний вызов на горячем пути, нет офлайна) |
| **SuperPoint + LightGlue** (или ALIKED+LightGlue, SIFT+RANSAC) | локальные признаки + матчинг | — | 512–1024 | n/a (не глобальный поиск) | 40–120 мс/пара при кэшированных признаках эталона | **геометрическая верификация топ-10, различение near-duplicates** |
| **PP-OCRv5 mobile (eslav/cyrillic) через ONNX Runtime** | OCR | — | кроп этикетки | — | 0,2–0,5 с | **текстовый канал: год, сладость, объём, винодельня** |

\* Ориентиры для 8 потоков x86 без AVX-512, будут уточнены бенчмарком на этапе 2 (`reports/bench_models.md`).

Почему не «только SigLIP 2» (рекомендация организатора): бенчмарки показывают, что даже лучшие zero-shot модели дают R@1 ≈ 80 % на чистых e-commerce фото; на полке с near-duplicates будет ниже. SigLIP 2 берём за основу (как рекомендовано) и добиваем precision локальными признаками и OCR.

Почему DINOv2/v3 вторым, а не одним: self-supervised признаки ловят «инстансную» похожесть (форма, композиция этикетки) и меньше зависят от семантики текста; в ансамбле с SigLIP на бенчмарках стабильно прибавляет 3–8 п.п. R@1. Дёшево на CPU при 224 px. Если бенчмарк на нашей валидации не покажет прироста — отключаем флагом.

Почему локальные признаки обязательны: этикетка — плоский объект; гомография между кропом запроса и эталоном с ≥ 30 инлайерами практически исключает ложное совпадение с другой этикеткой и хорошо ранжирует внутри серии, где меняется 1–2 слова (разные слова → меньше инлайеров в области текста). Это классический приём (Vivino, Google Lens используют геометрическую верификацию). Признаки эталонов считаются офлайн; онлайн — одна экстракция на запрос + матчинг с топ-10.

Почему OCR остаётся усилителем: организатор допускает, что OCR увеличивает время; поэтому OCR работает только на кропе этикетки, параллельно с эмбеддингами, с жёстким таймаутом (по умолчанию 700 мс) и участвует в реранкере через атрибуты (год `20\d\d`, `полусухое|брют|…`, объём, токены названия/винодельни через `rapidfuzz`). Без OCR серии типа «Рислинг сухое / полусухое» с одинаковой этикеткой неразрешимы в принципе.

## 3. Итоговый выбор (v1)

| Слой | Технология | Конфиг по умолчанию |
|------|-----------|--------------------|
| Детекция бутылки/этикетки | Ultralytics YOLO11n, дообученный на ~300 авторазмеченных изображениях (разметка zero-shot OWLv2/Grounding DINO офлайн) | 640 px, CPU ≈ 40 мс. Этап 2 — fallback: центральный кроп + saliency |
| Глобальный эмбеддинг A | `google/siglip2-base-patch16-384` (image tower), L2-norm | 768-d, cosine. `SIGLIP_MODEL` переключается на `siglip2-so400m-patch16-naflex` при GPU |
| Глобальный эмбеддинг B | `facebook/dinov2-base` (или `dinov3-vitb16` при приемлемой лицензии/скорости), CLS+mean-patch | 768-d, cosine |
| Локальные признаки | SuperPoint + LightGlue (`kornia`/`lightglue` PyPI), MAGSAC++ гомография (OpenCV) | 1024 px по большей стороне, до 1024 точек |
| OCR | PaddleOCR PP-OCRv5 `eslav_mobile_rec` + `PP-OCRv5_mobile_det` через `rapidocr-onnxruntime` | только кроп этикетки, таймаут 700 мс |
| Текстовый поиск | PostgreSQL `pg_trgm` + `rapidfuzz` по нормализованным полям; текстовые эмбеддинги описаний для аналогов — `intfloat/multilingual-e5-small` (384-d) | |
| Векторное хранилище | PostgreSQL 16 + pgvector 0.8 (HNSW, cosine) — источник истины; в процессе — numpy-матрица (≤ 50k × 768 float32 = 150 МБ) для < 5 мс поиска | |
| Инференс | PyTorch 2.x CPU (+ `torch.compile`/ONNX Runtime при необходимости), fp32 на CPU, fp16 на GPU | `DEVICE=cpu|cuda` |
| Реранкер | Этап 2 — взвешенная сумма с ручными весами; этап 3 — логистическая регрессия / LightGBM на признаках пар (обучение на валидации + синтетике) | |
| Калибровка уверенности | Isotonic regression на `[score1, margin, inliers1, ocr_match1]` → `confidence` | пороги `match ≥ 0,75`, `not_found < 0,35` |

## 4. Мультивид эталона (ключ к доменному разрыву)

Для каждого эталонного фото индексируются несколько векторов на каждую модель:

1. `bottle_full` — бутылка по альфа-обрезке на нейтральном фоне.
2. `label_crop` — этикетка (детектор; fallback — эвристика 35–80 % высоты бутылки).
3. `label_aug_k` (k = 4–8) — этикетка/бутылка с синтетическими искажениями: перспектива ±20°, блик, размытие, гамма, композиция на случайный фон «полки», кроп.

При поиске score вина = max по его видам (потом агрегируется в реранкере). Это даёт большую часть прироста recall без обучения. Дообучение (LoRA на image tower SigLIP 2, contrastive «эталон ↔ полевое/синтетическое») — опциональный шаг этапа 3, включается только если accuracy@1 на валидации < 90 %.

## 5. План экспериментов (этап 2, `reports/bench_models.md`)

1. Recall@1/5/20 по каждой модели отдельно на валидационном наборе: bottle vs label crop vs multi-view.
2. Ансамбль A+B (среднее нормированных cosine) vs каждая по отдельности.
3. Реранк топ-20 локальными признаками: прирост accuracy@1, время.
4. Вклад OCR: accuracy@1 с/без, разбивка по near-duplicate парам.
5. Латентность по этапам на CPU (8 потоков) и на GPU (если доступен), p50/p95.
6. Решение о `so400m` vs `base`, DINOv2 vs DINOv3, включённости OCR — фиксируется в `configs/pipeline.yaml`.

## 6. Что отвергнуто и почему

- Только OCR + текстовый поиск — не выдержит декоративные шрифты, латиницу/кириллицу вперемешку, частично закрытые этикетки; постановка требует CV-компонент.
- VLM-реранкер (GPT/Gemini/Qwen-VL) на горячем пути — 2–6 с на запрос, внешняя зависимость, нестабильные ответы; допустим только как офлайн-инструмент авторазметки.
- Milvus/Qdrant/Elastic — избыточны при 50k векторов; pgvector рекомендован организатором и достаточен.
- Классификатор «2103 класса» — каталог растёт на 50 позиций в день, обучать заново нецелесообразно; retrieval добавляет позиции без переобучения.
