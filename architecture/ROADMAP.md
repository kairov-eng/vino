# План реализации в три этапа

Каждый этап заканчивается работающим артефактом и измеримыми критериями приёмки. Оценки трудоёмкости — для команды 2–3 человека.

## Этап 1. Загрузка и индексация данных (≈ 1 неделя)

Цель: воспроизводимо превратить экспорт Strapi в базу с карточками, эталонными изображениями и векторами.

Задачи:

1. Скелет репозитория `vino-svoe` по структуре из `ARCHITECTURE.md` §4; `docker-compose.yml` с `db` (pgvector) и `ml`; `configs/pipeline.yaml`; `.env.example`; `Makefile`.
2. `catalog/ingest.py`: чтение CSV (utf-8-sig, многострочные поля), дедупликация по slug, нормализация текста (`name_norm`, `winery_norm`), парсер slug (`slug_parser.py`) с тестами на ≥ 30 примерах из `DATA.md`.
3. `catalog/image_resolver.py`: sitemap → транслитерация → `manual_image_map.csv`; отчёт неразрешённых; тесты на известных парах (`Спуманте белый брют.webp` → `Spumante_belyj_bryut_d34e854a7b.webp`).
4. Загрузка `wineries_sitemap`, `*.geojson`, сопоставление регионов.
5. Миграции БД (alembic) по схеме §6; `wine_image_groups` для 14 групп общих фото.
6. `catalog/views.py`: альфа-обрезка, эвристический кроп этикетки (детектор — этап 2), 4–8 аугментированных видов; сохранение миниатюр для отладки.
7. `pipeline/embed.py` (SigLIP 2 base, DINOv2 base), `pipeline/local.py` (SuperPoint), `pipeline/ocr.py` (PP-OCRv5 eslav ONNX) — офлайн-режим для индексатора; `catalog/indexer.py` с батчами и резюмируемостью.
8. `svoe_vino report`: сводка по каталогу и качеству эталонов (`reports/catalog_report.md`).
9. Копия `eval/` организатора в репозиторий; `data/val/` со структурой под собственную съёмку; начало съёмки полевых фото.

Критерии приёмки:

- `make ingest index` на чистой машине (CPU) проходит без ручных шагов ≤ 30 мин.
- В БД: 2103 `wines`, ≥ 2094 `wine_images`, 14 `wine_image_groups`, векторы обеих моделей для всех видов, локальные признаки для `label_crop`.
- Повторный запуск не пересчитывает неизменённые записи (лог показывает `skipped`).
- Юнит-тесты `slug_parser`, `image_resolver`, `ingest` зелёные.

## Этап 2. Страница проверки фото и диагностика (≈ 1,5–2 недели)

Цель: end-to-end поиск с прозрачной диагностикой; выбор конфигурации моделей по измерениям; совместимость со скриптом организатора.

Задачи:

1. `pipeline/runner.py` — оркестрация шагов с параллелизмом и таймаутами; `pipeline/normalize.py` с `HeuristicDetector`; `search.py` (in-memory индекс + pg_trgm); `rerank.py` с `LinearScorer`; `decide.py` с ручными порогами.
2. FastAPI: `/v1/eval/predict`, `/v1/scan?debug=1`, `/v1/wines/{slug}`, `/v1/health`, `/media`.
3. Диагностическая страница (`web/pages/debug.vue`, минимальный стиль): загрузка/камера → исходник, кропы, детекции; top-10 с эталонами и разложением score по сигналам; OCR; тайминги; решение. Пакетный режим по манифесту с таблицей метрик.
4. `eval/metrics.py`, `svoe_vino eval` — воспроизведение протокола организатора + accuracy@1, recall@5, F1@1/F1@5, margin, latency p50/p95; отчёт в `reports/`.
5. Бенчмарк моделей (`reports/bench_models.md`) по плану `TECH_CHOICE.md` §5: bottle vs label vs multi-view; SigLIP 2 base vs so400m; + DINOv2; + LightGlue; + OCR; CPU-латентность. Фиксация конфигурации в `configs/pipeline.yaml`.
6. Детектор `YOLO11n` для бутылки/этикетки: авторазметка ~300 изображений (эталоны + синтетика + собственные фото) zero-shot моделью, дообучение, замена `HeuristicDetector`.
7. Валидационный набор: ≥ 150 собственных фото ≥ 50 вин, разметка, публикация в `data/val/` (в git — только манифест и ответы, фото — отдельный архив).
8. Прогон `participant_test.sh` из bash (WSL/Git Bash) против сервиса; проверка формата и таймаутов.

Критерии приёмки:

- `participant_test.sh` отрабатывает без ошибок, `predicted_slug` ≠ `null` для всех запросов.
- На валидационном наборе: accuracy@1 ≥ 80 %, recall@5 ≥ 95 %, p95 ≤ 3 с на CPU.
- Диагностическая страница показывает для любого фото полный разбор за один запрос.
- `reports/bench_models.md` содержит обоснованный выбор конфигурации с цифрами.

## Этап 3. Полное решение по постановке (≈ 2–3 недели)

Цель: продуктовый сценарий в стилистике «Своё Вино», функция после поиска, точность 90 %+, документация и демо.

Задачи:

1. Качество: `LearnedScorer` (логрег/LightGBM на парах из валидации + синтетики), калибровка `confidence` (isotonic), подбор порогов по ROC на валидации; hard-negative анализ по near-duplicate сериям; при accuracy@1 < 90 % — LoRA-дообучение image tower SigLIP 2 на contrastive-парах «эталон ↔ полевое/синтетика».
2. Скорость: профилирование, `torch.compile`/ONNX для эмбеддеров, ограничение потоков, кэш локальных признаков; профиль `gpu` в compose.
3. Мобильный UI (Nuxt, mobile-first, токены стиля портала): экран сканирования (камера/галерея, индикатор), карточка вина (`wine/[slug]`, SSR), состояние `low_confidence` (карточка + «возможно, вы искали»), `not_found` (аналоги с объяснением), обратная связь «Это оно?».
4. Функция после поиска: «Цифровой сомелье» (`/v1/sommelier`, провайдеры LLM + fallback), «Аналоги из других виноделен» (`/v1/wines/{slug}/similar`), «Регион на карте» (geojson).
5. Инкрементальное пополнение каталога: `ingest`/`index` по новому CSV, `POST /v1/admin/reload`, документация процесса (50 позиций/день).
6. Наблюдаемость: структурированные логи, `/v1/metrics`, `scan_log`/`feedback` в БД.
7. Документация: `README.md` (сетап, запуск, переменные окружения, ограничения), актуализация `ARCHITECTURE.md`, `reports/public_eval_*.md`; фиксация версии (тег), видео-демо ≤ 7 мин, презентация по шаблону.

Критерии приёмки:

- accuracy@1 ≥ 90 % на валидационном наборе; margin между верным top-1 и top-2 стабильно положительный (медиана ≥ 0,2 нормированного score); ECE калибровки ≤ 0,08.
- Сценарии П1–П3 из `TZ.md` проходят на телефоне в мобильном браузере.
- Полный запуск с нуля: `git clone` → `make setup ingest index` → `docker compose up` → скрипт организатора → отчёт метрик; всё описано в README.
- Функция после поиска работает офлайн (fallback) и с внешним LLM (при наличии ключа).

## Зависимости и параллелизация

- Съёмка валидационных фото начинается на этапе 1 — без неё этап 2 не может выбрать конфигурацию.
- UI-разработчик на этапе 2 делает диагностическую страницу и заготовку дизайн-токенов, на этапе 3 — продуктовые экраны.
- Дообучение моделей (этап 3, п.1) — только по результатам бенчмарка этапа 2.
