# Как работает поиск вина по фото (Findwine)

**Проект:** Vino Svoe — каталог российских вин и сервис, который по фотографии бутылки пытается найти то же вино в каталоге.

**Для кого этот документ:** для человека, который **не** обязан знать код. Здесь объясняется алгоритм: что делает система, почему она приняла решение, какие настройки действуют **на оценке**.

**Код:** `backend/app/pipeline/findwine.py` и соседние модули.  
**Версия алгоритма:** см. `ALGORITHM_VERSION` в `backend/app/pipeline/version.py` (сейчас **0.104.x**; номер и дата также в UI «Время обработки»).  
**Дата этого описания:** 2026-09-29.

**Эталон настроек для оценки:** файл [`backend/pipeline_settings.json`](../backend/pipeline_settings.json). Именно его значения приведены в разделе [«Настройки на оценке»](#настройки-на-оценке-эталон). Если в админке сканера что-то поменять — поведение изменится; для приёмки ориентируйтесь на этот JSON (или снимок `status.settings` у конкретного скана).

Подробности текстового слоя fin1 (TextScore, hard mismatch, F1): [`algorithm-ocr-text-finalscore-f1.md`](algorithm-ocr-text-finalscore-f1.md).

---

## Зачем нужен этот пайплайн

Пользователь фотографирует бутылку (или этикетку). Система должна ответить:

1. **Какое вино из каталога это скорее всего?** — одно «победившее» вино, либо честный отказ («не нашли»).
2. **Какие ещё варианты** нашлись визуально (топ‑N по похожести картинки) и кто попал в зону «похоже, но не матч».

Одной «похожести картинки» мало: у одной винодельни этикетки часто очень похожи. Одного распознанного текста тоже мало: OCR ошибается, а в каталоге много вин с похожими словами («Каберне», «сухое», «брют»). Поэтому пайплайн **сначала сужает круг по картинке**, потом **проверяет текст и жёсткие несовместимости**, и только потом выбирает победителя.

## Настройки на оценке (эталон)

Источник: `backend/pipeline_settings.json` на момент 2026-09-29.  
Это **финальный вариант для оценки решения**. Ниже — смысл по-русски; полный JSON — в файле.

### Что реально включено

| Параметр | Значение на оценке | Что это значит |
|----------|--------------------|----------------|
| Детекция этикетки | YOLO `bottle_label`, `use_yolo=true` | Ищем бутылку и этикетку; склеиваем полоски |
| Fallback «весь кадр» | `yolo_fallback_full_image=true` | Если YOLO не нашёл этикетку — берём весь кадр |
| Gemini как запасной детект рамки | `label_detect_gemini=true` | Доп. вариант поиска рамки (OpenAI детект выкл.) |
| Размер кадра | `normalize_max_side=800` | Длинная сторона JPEG ≤ 800 px |
| Embeddings | **SigLIP2**, `use_dinov3=false` | Второй канал DINOv3 **выключен** |
| Устройство embedding | `embedding_device=gpu` | Сначала GPU (HF); при сбое/таймауте — свой CPU endpoint |
| Кеш embedding на CPU | `embed_cpu_use_cache=true` | На CPU-endpoint можно читать Redis-кеш (`use_cache=1`) |
| **Сколько кандидатов по картинке** | **`candidates_top_n=10`** | Не «топ‑20» и не 40: на оценке берём **10** ближайших по SigLIP2 |
| Reuse прошлых поисков | `reuse_previous_searches=false` | Прошлые сканы **не** подмешиваются |
| OCR | только **Google Vision** (`use_google_vision_ocr=true`, остальные OCR выкл.) | Gemini/OpenAI/Yandex/Qwen/DeepSeek OCR не вызываются |
| Какой OCR-текст идёт в XGB / exclusive | `final_ocr=google_vision` | Берётся текст **одного** движка, без склейки всех OCR |
| Текстовые методы | только **`xgb`** в `text_match_methods` | fin1 / fin2 / Cross-Encoder **не** считаются как отдельные судьи |
| **Кто выбирает победителя** | **`final_score_method=xgb`** | Судья — XGBoost (`XGB_fin`) |
| Пороги XGB | match **0.11**, similar **0.08** | Победитель только если score **строго выше** 0.11 |
| «Мёртвый» XGB | `xgb_dead_max=0.10` | Если у всех выживших max XGB ≤ 0.10 — не брать XGB_fin как итог (fallback Soft TF‑IDF / cosine) |
| Веса смеси текст+картинка | text **0.65**, cosine **0.45** | `XGB_fin = 0.65×XGB + 0.45×cosine` (в зоне match/similar) |
| Пустой OCR → победа по картинке | порог cosine **0.86** | Только если max cos ≥ 0.86 |
| HSV / ColorDelta | оба **выкл.** (`compute_hsv=false`, `compute_color_delta=false`) | Цвет **не** считается и **не** отсекает |
| Exclusive (взаимоисключающие слова) | всегда в пайплайне | Транслит форм: `exclusive_use_translit=true` |
| Снятие hard reject при сильных скорах | вкл.: cos≥**0.90** и xgb≥**0.70** | Иначе exclusive/label-text reject обнуляет кандидата |
| Быстрый текстовый матч | `fast_text_match=true` | Ускорение exclusive / Soft IDF (логика та же) |
| Детали поиска в UI | `show_search_details=false` | Обычному пользователю — упрощённый вид |

Пороги fin1 / fin2 / CrEnc в JSON есть «про запас», но на оценке эти методы **не включены** в `text_match_methods` и **не** являются Final score.

### Как читать зоны match / similar / none

Функция в коде (`score_band`):

| Зона | Условие для оценки `S` | Может ли стать победителем? |
|------|------------------------|-----------------------------|
| **match** | `S > порог match` | да |
| **similar** | `порог similar ≤ S ≤ порог match` | нет (только «похоже») |
| **none** | `S < порог similar` | нет |

Для XGB на оценке: match при `XGB_fin > 0.11`, similar при `0.08 ≤ XGB_fin ≤ 0.11`.

## Карта шагов одним взглядом

Один запрос `POST /api/findwine` (или `POST /v1/eval/predict` для приёмки):

1. Сохранить фото и привести кадр (EXIF, HEIC→JPEG, max side).
2. Найти рамку этикетки (YOLO bottle+label) и вырезать её.
3. Посчитать embedding SigLIP2 → **топ‑10** вин из каталога (на оценке).
4. Параллельно OCR Google Vision.
5. Exclusive lexicon: отсечь кандидатов без «той же формы» ключевых слов.
6. XGBoost: вероятность «то же вино» → `XGB_fin` (смесь с cosine).
7. Выбрать победителя **только из зоны match** по XGB; иначе — отказ (или особый случай пустого OCR).

Многое идёт параллельно; порядок выше — логический.

## 1. Приём фото и подготовка кадра

Фото пишется в `search_photos` и на диск как рабочий JPEG.

- HEIC и т.п. → RGB JPEG.
- На оценке длинная сторона ≤ **800** px.
- Появляются: картинка с рамками (`*_crops.jpg`) и кроп этикетки (`*_label.jpg`) — дальше в embedding и OCR идёт именно кроп (или весь кадр при fallback).

---

## 2. Как находится этикетка на фото

На оценке: **YOLO «бутылка + этикетка»**.

### Режим «бутылка + этикетка» (кратко)

1. Рамки делятся на бутылки и этикетки.
2. Отбрасываются «сиротские» этикетки (мусор вне бутылок).
3. Этикетки одной бутылки склеиваются в одну рамку.
4. Выбирается primary: предпочтение бутылке с сильной этикеткой на корпусе; иначе кроп корпуса бутылки.
5. Если ничего не нашли и включён fallback — **весь кадр**.

Подробности склейки и primary — в коде `yolo_detect.py` и в журнале версий 0.46–0.97.

---

## 3. Поиск похожих вин по картинке

**Embedding** — числовой отпечаток картинки. В каталоге заранее посчитаны отпечатки по фото этикеток. Сравнение — **cosine** (ближе к 1 = похожее).

На оценке:

- канал **только SigLIP2**;
- из базы берётся **`candidates_top_n = 10`** ближайших вин **с эмбеддингом**;
- DINOv3 выключен → список кандидатов = эти 10 (плюс позже фильтры/скоры).

> Важно: в старых текстах и в схеме ARCHITECTURE часто писали «топ‑20». Это **историческое** число. На оценке работает **10**. Допустимые значения настройки: 10 / 20 / 30 / 40.

Вина **без** строки в `embeddings_siglip2` в этот топ **не попадут** — см. [ограничения](#известные-ограничения).

### Геометрия (ключевые точки)

В JSON есть флаги `geometry_siglip2` / `geometry_dinov3`. Это **опциональная** проверка совпадения деталей картинки: результат пишется на карточки кандидатов для отладки. **Победителя она сама не выбирает** и порогом не режет (в отличие от exclusive / XGB). На оценке DINOv3 выкл., геометрию по SigLIP2 в эталоне тоже можно считать вспомогательной.

### Переиспользование прошлых поисков

На оценке **выключено**. Если когда‑нибудь включить: при похожем старом скане (cosine ≥ 0.5) победитель того скана может добавиться 11‑м кандидатом, а его Google Vision OCR — подставиться в текст.

---

## 4. Цвет этикеток (HSV / ColorDelta)

| Режим | На оценке | Отсекает кандидатов? |
|-------|-----------|----------------------|
| HSV (Бхаттачария) | **выкл.** | Только если включить расчёт HSV и пороги soft/hard reject |
| ColorDelta (CIEDE2000 доминирующего цвета) | **выкл.** | **Нет** — это поле на карточке для глаз, не gate |

Итого на оценке цвет **не участвует** в решении. Упоминание ColorDelta как «gates» в старых архитектурных текстах к текущему эталону **не относится**.

---

## 5. Чтение текста (OCR)

На оценке вызывается **только Google Vision**.

### Как выбирается «текст запроса» для exclusive и XGB

С версии ~0.56 / 0.60.4 система **не склеивает** все OCR в одну кашу.

1. Настройка `final_ocr` (на оценке: `google_vision`).
2. Функция `resolve_final_ocr` берёт текст **этого** движка, если он есть.
3. Если выбран `auto` — приоритет как при обучении XGB: google_vision → gemini → openai → …

Именно этот один текст идёт в exclusive lexicon и в признаки XGBoost. Перед сравнением текст нормализуется (регистр, пробелы, омографы латиница→кириллица и т.п. — см. `ocr_homoglyphs.json`).

### Пустой OCR

Если текста нет:

- exclusive / XGB / fin* **не** гоняются;
- победитель возможен только по **max cosine**, если он ≥ `empty_ocr_cosine_threshold` (**0.86** на оценке);
- иначе — «не найдено».

## 6. Взаимоисключающие слова (exclusive lexicon)

Фильтр среди **уже отобранных по картинке** кандидатов (не поиск по всему каталогу).

### Правило

Если в OCR запроса нашлась форма из справочника (цвет / тип / сорт / винодельня), у кандидата должна найтись **та же форма** (не «любой синоним смысла»). Иначе кандидат **hard reject**: не может победить, финальные fin обнуляются.

На оценке включён транслит форм (`exclusive_use_translit=true`): часть латинских/кириллических написаний сопоставляется.

Для сортов и виноделен используется разбор **длинных фраз сначала** (например «Каберне Совиньон» раньше, чем голое «Каберне») — версия 0.104.

### Снятие reject при очень сильных скорах

Если включено `hard_reject_ignore_high_scores` (на оценке **да**): при cosine ≥ **0.90** и xgb_score ≥ **0.70** hard reject (exclusive / label-text / HSV hard) **снимается** — система допускает, что OCR «опечатался», а картинка и XGB очень уверены.

### Чувствительность к OCR

Сравнение форм — по нормализованному вхождению / индексам токенов, **не** «нечёткий поиск с опечаткой в одну букву» как основной режим. Ошибка OCR («Каберне» → «Каберие») может отсечь верного кандидата, если не сработал bypass по высоким cos+XGB. Это осознанный trade-off «не выдать красное вместо белого».

## 7. XGBoost и выбор победителя

На оценке судья — **только XGB**.

1. Модель (каталог `XGB_MODEL_DIR`, abs_v14) даёт `xgb_score` = P(то же вино) по признакам OCR↔label (+ сигнал cosine/ранга).
2. Считается  
   `XGB_fin = 0.65 × XGB + 0.45 × cosine`  
   если XGB в зоне match или similar; иначе / при hard reject → `XGB_fin = 0` (в UI может остаться «серое» значение до reject).
3. Победитель — кандидат с **максимальным XGB_fin среди зоны match** (`XGB_fin > 0.11`).
4. Если зона match пуста — **победителя нет** (even если есть similar). Система **не** подставляет молча «первое по картинке» (кроме пустого OCR с высоким cosine).

### «Мёртвый XGB»

Если у выживших кандидатов все `xgb_score` ≤ `xgb_dead_max` (0.10), итог по XGB_fin не берут: запасной путь Soft TF‑IDF (fin2) или снова опора на cosine — см. код и notes 0.90 / 0.101.

### fin1 / fin2 / Cross-Encoder / OpenAI txt

В коде и UI они есть, но **на оценке выключены** как Final score. Кратко:

- **fin1** — классический TextScore сущностей OCR ↔ карточка + cosine (детали в `algorithm-ocr-text-finalscore-f1.md`).
- **fin2** — Soft TF‑IDF + cosine.
- **CrEnc** — cross-encoder по паре текстов.
- **OpenAI txt** — LLM-сравнение (отдельный шаг, не эталон оценки).

## 8. Режим оценки (`/v1/eval/predict`)

| Вопрос | Ответ |
|--------|--------|
| Какой endpoint? | `POST /v1/eval/predict` (multipart `image`) → `{"slug": "..."}` или `slug: null` |
| Что внутри? | Тот же `run_findwine(..., eval_mode=1)` |
| Отличие от обычного скана | **Не** считаются аналоги; **выбор победителя такой же**, как при `eval=0` (только зона match) |
| Принудительный top‑1 с низким score? | **Нет** (убрано в 0.99.0) |
| Если матча нет | В ответе **`slug: null`** (не «всегда какой‑нибудь лучший») |

Старое утверждение в ARCHITECTURE ADR «eval всегда отдаёт лучший slug» **устарело** относительно текущей логики 0.99+: отдаётся slug победителя match, иначе null.

Обычный UI-скан: `POST /api/findwine` с `eval=0` (по умолчанию).

## Известные ограничения

1. **Нет эмбеддинга — не найти по этому пайплайну.** В каталоге ≈ 2103 вина, SigLIP2-эмбеддингов ≈ 2084. Кандидаты берутся **только** из ANN по картинке. Вина без embedding **не попадут** в топ‑N; отдельного «поиска по тексту по всему каталогу» нет. (Фраза в старых README про «только текстовый канал» для вин без фото к текущему hot-path findwine **не относится**.)

2. **Recall ограничен картинкой.** Если верного вина нет в топ‑N (на оценке N=10), XGB его уже не увидит.

3. **Exclusive чувствителен к форме слова в OCR.** Опечатка OCR может отсечь верного; частично смягчается нормализацией, транслитом и bypass при очень высоких cos+XGB.

4. **Две этикетки / два slug на похожих фото.** Система всё равно выбирает один primary-кроп и один победитель match (или отказ). Отдельной ветки «вернуть оба slug» нет.

5. **Зависимость от внешних сервисов.** Google Vision и (при GPU) Hugging Face: при недоступности качество/скорость падают или срабатывает CPU fallback для embedding.

## Короткий итог (как на оценке)

1. Вырезать этикетку (YOLO bottle+label, при нужде — весь кадр).  
2. Найти **10** визуально похожих вин (SigLIP2).  
3. Прочитать текст **Google Vision**.  
4. Отбросить несовместимых по exclusive (с возможным bypass при сильных скорах).  
5. Оценить XGBoost → `XGB_fin`; победитель только при **match** (`XGB_fin > 0.11`).  
6. Если матча нет — честный отказ (`slug: null` на `/v1/eval/predict`).  
7. Если OCR пуст — только высокий cosine (≥ 0.86) может дать победителя.
